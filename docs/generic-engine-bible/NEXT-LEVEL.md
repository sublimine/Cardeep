## discovery-trust — 12 mejoras
### Selector activo de lista ortogonal por gradiente de coverage_lower (value-of-information loop)
- **Qué:** Bucle cerrado de active-learning que en CADA build rankea TODA lista ortogonal candidata (GLEIF, Wikidata, un nuevo corpus de dorks, un localizador OEM, schema.org/CommonCrawl...) por la REDUCCION ESPERADA del intervalo nacional si se ingiere — computando la reduccion de varianza esperada por estrato a partir del delta-method Fienberg que YA vive en estimators.py:243-245 — y le dice al scheduler de descubrimiento (discover_schedule.py) QUE lista adquirir a continuacion para comprar el maximo coverage_lower por unidad de coste. Convierte 'anade mas listas' de ciego a argmax-VoI; cierra el loop con el detector de saturacion (mejora #12): cuando el VoI marginal de toda candidata ~0, el pais esta exhausto.
- **Por qué inalcanzable:** Ningun humano ni equipo rankea 25+ fuentes candidatas por su efecto marginal sobre un intervalo de captura-recaptura ESTRATIFICADO (provincia x segmento) y lo re-deriva cada build; es diseno experimental bayesiano sobre el estimador VIVO que solo se sostiene automatizado y reproducible. Eleva 'exhaustividad' de 'lo intentamos con ganas' a 'gastamos esfuerzo demostrablemente donde el intervalo encoge mas'. La biblia ya pide cadencia auto-sintonizada (01:next_level) y saturacion (07:next_level) pero NADIE conecta la DECISION-de-que-lista al gradiente del IC.
- **Herramienta:** BoTorch (acquisition functions = expected information gain sobre el espacio de listas-candidatas) (MIT, €0=True) — https://github.com/pytorch/botorch
- **Alternativas:** scikit-activeml, modAL, MABWiser, Ax
- **Ruta €0:** CPU puro, todo permisivo; el gradiente de varianza ya es computable del delta-method en estimators.py — el VoI es un re-uso, no infra nueva. Sin GPU, sin SaaS.
- **Verificación:** Backtest: re-jugar builds historicos (serie append-only de exhaustiveness_estimate) y confirmar que la lista que el selector HABRIA elegido es la que empiricamente encogio mas coverage_lower. 2a via: cross-check del ranking VoI contra el brute-force 'anade-una-lista-y-recomputa' (deben coincidir dentro de tolerancia). 3a via: unit test sobre estratos sinteticos con N conocido (el selector converge al N verdadero gastando menos listas que el orden aleatorio).

### Estimador robusto para listas SIN solapamiento (SparseMSE) — sella el pais de fuentes delgadas
- **Qué:** Anadir SparseMSE como ruta de estimador de primera clase para estratos donde pares de listas tienen CERO solapamiento — el fallo no-ES exacto que la auditoria marco CRITICAL: DE/IT/PT con solo GEO+OEM => K<3 => piso Chapman, confidence forzado 'low', casi nada sella. SparseMSE (Chan-Silverman-Vincent 2019) maneja la no-existencia del MLE, parametros en -inf y la no-identificabilidad, recuperando un intervalo finito donde el log-lineal Python actual degenera a observed-only/inf-CI. Corre por el mismo Rscript subprocess bridge que ya existe (estimators_r.py).
- **Por qué inalcanzable:** Elegir y aplicar correctamente la maquinaria sparse-MSE por estrato, detectar no-identificabilidad y plegarlo en un roll-up nacional con varianzas que suman es captura-recaptura nivel-doctoral hecho AUTOMATICAMENTE en 200+ estratos cada build; ningun equipo ajusta a mano modelos log-lineales sparse en cada celda provincia x segmento. Es justo lo que hace SELLABLE un pais de ecosistema de fuentes mas pobre que ES.
- **Herramienta:** SparseMSE: Multiple Systems Estimation for Sparse Capture Data (GPL (>=2), €0=True) — https://cran.r-project.org/package=SparseMSE
- **Alternativas:** dga (Bayesian model averaging), LCMCR, conting
- **Ruta €0:** Corre bajo el bridge Rscript existente (estimators_r.py:86-129, patron ya probado); R es gratis; degrada graceful si R ausente (igual que hoy). Sin coste.
- **Verificación:** Cross-check SparseMSE vs log-lineal Python en estratos CON solapamiento (deben coincidir dentro de tol=0.25, la puerta de distrust ya existe estimators_r.py:175-193). En estratos sinteticos de solapamiento-cero confirmar que devuelve intervalo finito donde Python da inf-CI. R como 2a via ortogonal de mecanismo distinto (model-selection vs Bayesian).

### Promedio de modelos bayesiano (dga) — el sello deja de depender de UN modelo elegido por BIC
- **Qué:** Aumentar el unico log-lineal greedy-por-BIC (estimators.py:217-236) con Bayesian Model Averaging sobre las estructuras de interaccion (dga), produciendo un POSTERIOR de N por estrato que YA integra la incertidumbre de seleccion-de-modelo en el intervalo. El CI honesto deja de ser condicional a un set de interacciones elegido; la cota inferior del sello se toma del cuantil 2.5% del posterior promediado. dga es de Johndrow/Lum/Ball (Human Rights Data Analysis Group), construido exactamente para recuentos defendibles bajo incertidumbre de dependencia entre listas.
- **Por qué inalcanzable:** Integrar sobre el espacio completo de estructuras de dependencia entre listas y propagar eso a un intervalo nacional estratificado con varianzas entre-estrato es el estimador que solo sobrevive automatizado+reproducible; un humano elige UN modelo y subestima la incertidumbre — precisamente el sesgo que invalida un sello. HRDAG lo usa para recuentos de victimas en tribunales: el estandar institucional de 'numero que aguanta un interrogatorio adversarial'.
- **Herramienta:** dga: Capture-Recapture Estimation using Bayesian Model Averaging (GPL (>=2), €0=True) — https://cran.r-project.org/package=dga
- **Alternativas:** LCMCR, SparseMSE, PyMC
- **Ruta €0:** Bridge Rscript; CPU; gratis. dga + LCMCR + SparseMSE forman un TRIO de 2a via (model-averaging / latente / sparse) sobre el mismo input freqs.
- **Verificación:** La mediana del posterior dga debe coincidir con el punto log-lineal dentro de tol; coverage_lower derivado del cuantil 2.5% de dga vs ci_high Python — el sello usa el MAS conservador. Validacion publicada de HRDAG (tribunales) como referencia externa del metodo.

### Censo externo VINCULANTE como margen-conocido (population-with-known-margin) — convierte masa uncertified en certified
- **Qué:** Implementar el objetivo Fase-4 hoy SIN implementar (seal.py:42-47 ignora n_external): inyectar el ancla censal del pais como TOTAL MARGINAL CONOCIDO / offset Poisson (log(n_external)) en el ajuste captura-recaptura, de modo que los estratos que hoy fallan IDENT_CAP (bajo solapamiento => uncertified, descartados) obtengan N fijado por un mecanismo INDEPENDIENTE (registro/fiscal), trasladando masa de uncertified a certified SIN inventar dato. El gate de sello pasa a coverage_lower>=0.95 Y census-consistent. Es la palanca que el diseno 07 nombra como next_level #1 pero sin herramienta concreta — aqui se mina: el margen-conocido se modela como una pseudo-lista de total fijo via dga/SparseMSE o un offset en PyMC.
- **Por qué inalcanzable:** Combinar estadistica de censo (margen conocido) con captura-recaptura por (region x segmento) y recomponer a un intervalo nacional con varianzas sumadas es metodologia-de-censo FUSIONADA con MSE — sostenible solo build-a-build, reproducible, jamas a mano. Es la diferencia entre 'el modelo cree que cubrimos 95%' y 'un mecanismo fiscal independiente CONFIRMA el denominador'.
- **Herramienta:** dga / SparseMSE (inyeccion de margen-conocido via el bridge R existente) (GPL (>=2), €0=True) — https://cran.r-project.org/package=dga
- **Alternativas:** PyMC, Rcapture
- **Ruta €0:** R/PyMC CPU; el CSV de ancla YA existe por pais (countries/<CC>/census/, contrato de 8 tests). Sin coste nuevo.
- **Verificación:** Sobre ES: fijar con DIRCE debe MANTENER sellados los estratos ya sellados y SOLO ANADIR los nuevos-identificados (monotonia, cero regresion — golden). El ratio N_hat/n_external debe quedar en 0.7-1.4 por construccion. Golden test de que las transiciones uncertified->certified son census-driven, no threshold-gamed (auditoria adversarial).

### Sello criptograficamente reproducible y ATESTIGUADO (in-toto + Sigstore/rekor) — verificable por terceros sin confiar en nosotros
- **Qué:** Cada build de sello emite una atestacion in-toto que liga {git SHA del codigo, content-hashes de TODO input (census CSV, matriz de captura, membresias de lista, versiones de estimador)} -> {coverage_lower, CI, N_hat por estrato}, firmada y anexada a un transparency log Sigstore/rekor (ledger inmutable, tamper-evident, con prueba de inclusion). CUALQUIER tercero (auditor, regulador del pais, comprador) puede despues PROBAR 'este 80,5% salio exactamente de estos inputs y este codigo' — sin screenshot, sin dashboard, sin confiar en nosotros. El sello deja de ser una afirmacion y pasa a ser un CERTIFICADO no-repudiable.
- **Por qué inalcanzable:** Una afirmacion de cobertura re-verificable independientemente desde un ledger publico tamper-evident — no una captura de pantalla — es infraestructura supply-chain-grade que ningun censo manual ni equipo de analistas produce. Es 'jugar en otra liga' (mandato owner): la correccion no depende de confiar en quien publica, la impone y prueba la maquina criptografica. in-toto graduo en CNCF (2025-02-10), es el estandar industrial de provenance.
- **Herramienta:** in-toto (atestacion de provenance del build de sello) (Apache-2.0, €0=True) — https://github.com/in-toto/in-toto
- **Alternativas:** Sigstore rekor (transparency log), cosign, SLSA provenance, ml-metadata (MLMD)
- **Ruta €0:** in-toto + cosign (keyless via OIDC gratis, o clave auto-gestionada); rekor public-good instance es gratis, o self-host; CPU-only. Sin coste.
- **Verificación:** Re-correr un build desde los content-hashes atestiguados => coverage_lower BYTE-identico (gate de reproducibilidad). 2a via adversarial: alterar UNA fila del census => la verificacion de la atestacion FALLA. 3a via: prueba de inclusion en rekor chequeada en CI cada push.

### api-schema-fuzz (Schemathesis — fuzzing property-based del contrato, auto-detecta 500s y bleed)
- **Qué:** Testing dirigido por el schema OpenAPI que FastAPI ya genera: Schemathesis genera miles de casos por endpoint (los 18+) desde el schema, encontrando automáticamente 500s en edge cases, respuestas que violan el contrato documentado, y — con checks stateful y un hook de país — fuga cross-country. Va mucho más allá del 'OpenAPI snapshot test' del next_level: no congela la forma, ATACA el comportamiento.
- **Por qué inalcanzable:** El snapshot test del next_level solo detecta cambios de forma; no encuentra el 500 que un province_code raro dispara, ni la respuesta que miente respecto al schema. Schemathesis fuzz-ea con property-based (Hypothesis) y halla bugs que ningún test escrito a mano cubre — incluido el bleed de país si se le da el invariante. Es el inquisidor automático del contrato, corriendo en cada push. Nivel inalcanzable: el contrato del censo se auto-ataca y se auto-certifica, no se confía.
- **Herramienta:** schemathesis/schemathesis (MIT [VERIFIED], €0=True) — https://github.com/schemathesis/schemathesis
- **Alternativas:** apiaryio/dredd, microsoft/restler-fuzzer, HypothesisWorks/hypothesis
- **Ruta €0:** Schemathesis = librería/CLI Python MIT €0 en CI. Consume el /openapi.json que FastAPI ya expone. Cero infra, cero coste.
- **Verificación:** (1) Cero 500s no documentados en N=10k casos generados. (2) Conformance: ninguna respuesta viola el schema (forma garantizada por máquina). (3) Bleed: un check custom asserta que toda respuesta con dimensión país solo trae ese país (cierra los leaks CRITICAL del verdict mecánicamente). ### api-breaking-change-gate (oasdiff — 'el contrato es genérico entre países' como invariante mecánico)
- **Qué:** CI que diffea el OpenAPI spec entre el commit base y HEAD con oasdiff y FALLA si hay un breaking change (campo eliminado, tipo cambiado, parámetro requerido nuevo). Convierte la afirmación del engine_invariant 'el binario de la API es idéntico entre países / el contrato es country-invariante' de promesa a garantía verificada en cada push.
- **Por qué inalcanzable:** El next_level propone un 'snapshot que congela la forma' — frágil y manual. oasdiff entiende SEMÁNTICA de breaking changes (no solo diff textual) y es el estándar para gating de API en CI. Garantiza que añadir un país jamás rompe el contrato que un consumidor pan-EU ya usa. Es el guard que hace cumplir el invariante de genericidad del servido, igual que el golden cross-country hace cumplir el aislamiento de país. Nivel inalcanzable: la estabilidad del contrato es mecánica, no disciplinada.
- **Herramienta:** oasdiff/oasdiff (Apache-2.0 [VERIFIED], €0=True) — https://github.com/oasdiff/oasdiff
- **Alternativas:** OpenAPITools/openapi-diff, opticdev/optic
- **Ruta €0:** oasdiff = binario Go Apache-2.0 €0 con GitHub Action oficial. Consume el openapi.json generado. Cero infra, cero coste.
- **Verificación:** (1) Romper a propósito un endpoint (quitar un campo) → el gate falla (probar el guard rompiéndolo, vía-b ANTI-DRIFT). (2) Añadir país (aditivo) → 0 breaking changes (el invariante de genericidad se sostiene). (3) Doble vía: oasdiff y openapi-diff sobre el mismo par de specs coinciden en el veredicto.

### slo-perf-gate (sub-50ms CERTIFICADO — load test en CI que falla si p99>50ms)

Un SLO de latencia mecanizado en CI es práctica de equipos de plataforma serios, aquí €0. Hace que la promesa de velocidad sea estructural: no se puede mergear código que ralentice el censo. Nivel inalcanzable: el rendimiento es un contrato probado en cada push, no una medición puntual olvidada.
- **Herramienta:** tsenart/vegeta (MIT [VERIFIED], €0=True) — https://github.com/tsenart/vegeta
