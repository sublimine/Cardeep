## Estimacion cobertura (7.035 webs)
Honest extrapolation from the 90-site sample (denominator = full 7035, accepting sampling error ±~6pp at n=90). Real car dealers: 45/90 = 50% -> ~3,500 genuine dealers in the 7035 (the rest is ~33% confirmed business-noise + ~14% dead/walled-uncertifiable that should be re-probed/cleaned, not scraped). Auto-extractable €0 without JS: 35/90 of ALL sites = 38.9% -> ~2,736 dealers harvestable today by the generic cascade. Of those, 28/35 (80%) yield per-vehicle URLs straight from a sitemap = ~2,200 dealers drainable on the cheapest path alone. Cars: detectable dealers in the sample visibly range from ~6-9 (autodcmocasion) to 100-200+ (carcitycoches +100, grupobeniautos 188, quadis/ocasionplus-scale red nacional in the thousands). Using a deliberately conservative blended mean of ~40-60 live cars per detectable dealer (median storefront ~20-40, dragged up by a few large redes/grupos), 2,736 dealers -> roughly 110k-165k NEW vehicle listings (point-in-time), call it ~130k as a central estimate. An additional ~230 walled-but-real dealers (3.3% -> gruposeligrat/autoback/compraventacars class) are recoverable with €0 UA-rotation/header-mimic, adding low-tens-of-thousands more. This is NEW coverage on top of whatever is already drained, because these 7035 are explicitly undrained.

## Patrones dominantes
- SITEMAP-OF-CARS is the king signal: 28/35 detectable dealers (80%) expose per-vehicle (or per-listing) URLs in a dedicated sitemap. Recurring sitemap names: Vehica plugin 'vehica_car-sitemap.xml' (WP), DealerK/MotorK 'stock_listing_0 / auto_nuove_0 / auto_usate_0-sitemap.xml', WooCommerce 'product-sitemap.xml', Yoast/RankMath 'coches-sitemap.xml', and custom 'sitemap.vehicles.xml' / 'vehiculos.xml'.
- JSON-LD Vehicle/Car is RARE: only 4/35 (11%) emit schema.org Car/Vehicle (alcala534, crestanevada, carcitycoches, movilsa). It is a high-value bonus, NOT something to depend on. schema.org Microdata Vehicle appears too (autosantpedor). Org-level AutoDealer JSON-LD is common but carries no per-car data.
- CMS/platform mix among detectables is roughly even and finite: custom 12, DealerK/MotorK-family 12, WordPress 8, WooCommerce 3. The 'custom' bucket is itself templated SaaS, not snowflakes: DealCar.io Next.js with /buy/<uuid> + RSC self.__next_f payload (autosmontesinos, andradaocasion, carselect, automotoresatlantico), Google-storage Next SaaS /buy/<uuid> (geamotor, automoviles21), Laravel storefronts (ohanacars, quadis, grupodianium), Astro+Strapi (carcitycoches).
- SSR-cards-only fallback needed for 6/35 (palaciocasion via coches.* subdomain, autodeniamotors, compramostucocheyaa, autosjmg, peugeotalbox, frcarsocasion): no clean sitemap, but homepage/listing server-renders detail links (/coches/<slug>, /vehiculos/<slug>?id=N, detalles.php?vehiculo=) + price/km/fuel inline. Plus Next.js RSC inline payload (self.__next_f / dataLayer.push(vehicleData{})) is a recurring extractable vector when HTML cards are thin.
- WordPress is the dominant underlying CMS overall (~28% of the 90), and the 'Vehica' dealer plugin is the single most repeatable WP fingerprint for cars (hermanosvinaras, grupobeniautos, todocochesdeocasion).
- Detail-page spec encoding is consistent and JS-free: price 'NN.NNN€', 'NNN.NNN KM/km', combustible Gasolina/Diesel, year, all in raw HTML or in the Next RSC flight payload — extractable with regex/CSS, zero browser.

## Diseno del harvester (cascada de senales, €0, sin REGISTRY)
GENERIC €0 AUTO-HARVESTER (no per-dealer REGISTRY). The current family_generic_custom connector dies because it demands a hardcoded REGISTRY per dealer; the data proves that is unnecessary — 80% of real inventory hangs off 4-5 repeatable, self-describing signals. Design a single DealerProbe that runs a fixed signal cascade per domain, €0, no JS:

SIGNAL CASCADE (priority order, first hit that yields >=N vehicle URLs wins, but ALL run for enrichment):
1) SITEMAP DISCOVERY (primary, 80% hit). Fetch /robots.txt -> Sitemap: lines; else probe /sitemap.xml, /sitemap_index.xml. Recursively expand <sitemapindex>. Score child sitemaps by name regex (vehica_car|stock_listing|auto_(nuove|usate)|coches|vehicl|vehicul|product|inventario|buy|catalogo|precios|listado) and by URL-pattern density. Classify each <loc>: PER-VEHICLE if it matches per-car shapes (/buy/<uuid>, /coches/.../<id>/, /listado/<slug>, /vehiculos/<slug>, /precios/<m>/<mod>/<id>, /inventario/<slug>, /<marca>/<modelo>-<anio>-<km>-<id>, detalles.php?vehiculo=, /producto/<slug>). Emit those as the URL frontier.
2) JSON-LD ON LISTING+DETAIL (highest data quality when present, 11%). On homepage + any /coches*|/ocasion*|/vehiculos*|/inventario*|/catalogo* listing, parse every <script type=ld+json>; walk @graph; keep @type in {Car,Vehicle,MotorizedVehicle,Product+offers}. AutoDealer/Organization -> dealer identity only. This both extracts cars AND, when ItemList/AggregateOffer present, harvests the whole listing in one fetch (alcala534, crestanevada pattern: 24 Car nodes server-rendered).
3) MICRODATA / RDFa (autosantpedor pattern): itemtype=schema.org/Vehicle|Car|Offer scraped same as JSON-LD.
4) SSR CARD / RSC EXTRACTION (fallback for the 6 SSR-only + thin-card sites). On listing pages, extract anchor hrefs matching the per-vehicle shapes above; for Next.js, additionally parse inline RSC (self.__next_f.push payloads) and dataLayer.push(vehicleData{...}) / window.__NUXT__ / __NEXT_DATA__ JSON islands — these carry brand/model/version/price/km/fuel without executing JS.

PER-DETAIL EXTRACTION (shared by all paths): regex/CSS over raw HTML + any inline JSON for price (/(\d{1,3}[.\s]?\d{3})\s?€/), km (/(\d{1,3}[.\s]?\d{3})\s?km/i), fuel (gasolina|diesel|diésel|híbrido|eléctrico|gnc|glp), year, brand/model from slug + page title. Prefer structured (ld+json/RSC) field; fall back to regex.

FALLBACKS / ROUTING: per domain pick the first signal that returns >= 3 vehicle URLs; if sitemap returns only CATEGORY pages (ocasionplus, automovilessagunto pattern) demote to SSR-card crawl of those categories. If 0 signals fire AND page is brochure/iframe/captcha (marco iframe, compraventacars recaptcha, armerocar single page) -> mark inventory_source=external/js-gated, do NOT burn budget, queue for the (separate) JS-render tier.

DEDUP: canonical key = (registered_domain, normalized_detail_path) with uuid/id extracted; cross-check against VIN/matricula or (brand,model,year,km,price) tuple hash to collapse the same car appearing in sitemap + SSR card + ld+json. Honor <link rel=canonical>. Strip tracking query params.

PLUG-IN TO EXISTING FAMILY MACHINERY: register as ONE new family connector `family_generic_harvest` alongside family_generic_custom, exposing the same connector interface (discover()->url frontier, fetch(), parse()->vehicle records, dealer_meta()). The difference: its REGISTRY is not per-dealer but a small ordered list of SIGNAL RECIPES (sitemap-regex table, ld+json type set, RSC selectors, per-vehicle URL shapes). DealerK/MotorK, DealCar.io, Vehica, WooCommerce each become a RECIPE (auto-detected by fingerprint: 'dealerk'/'motork' tokens, app.dealcar.io footer, vehica-core, product_type_simple), so the 12 DealerK + 4 DealCar + WP-Vehica sites collapse to ~5 recipes covering the long tail. Existing delta/price/cdp_code/VAM zero-trust layers consume its output unchanged.
