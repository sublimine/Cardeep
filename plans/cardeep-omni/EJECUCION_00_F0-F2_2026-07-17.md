### 1.1 — Regresión real encontrada y corregida durante la propia verificación de F0

Mientras se observaban los logs en vivo del `heartbeat_tick` (11:59:41Z), `oem_hyundai_wholesale`
crasheó:
```
ModuleNotFoundError: No module named 'numpy'
  File "/app/pipeline/geocode.py", line 36, in <module>
    import numpy as np
```
**Causa raíz** [VERIFICADO, archivo:línea]: `pipeline/geocode.py` hace `import numpy as np` a
nivel de módulo (línea 36) — su propio docstring afirma "Dependencies: numpy only (already
installed)" — pero `numpy` estaba declarado SOLO en `requirements-dev.txt:7` (mal clasificado
ahí como dependencia de test: "vector / geo math in tests/..."), NUNCA en `requirements.txt`
(el que instala el Dockerfile). Alcance real: 11 módulos de `pipeline/platform/` importan
`pipeline.geocode` transitivamente —incluyendo DOS de los seis breakers de este mismo triage
(`oem_audi_wholesale`, `oem_nissan_mazda_honda_wholesale`) y ambos módulos de wallapop
(`wallapop_wholesale.py`, `wallapop_facet.py`)— es decir, toda imagen reconstruida desde
`requirements.txt` limpio crashea ~20% del registro de fuentes en el primer intento.

**Corrección aplicada** [file: `requirements.txt`]: añadido `numpy>=2,<3` como dependencia de
runtime (mismo pin que `requirements-dev.txt`), con comentario citando el hallazgo. Rebuild 2:
`cardeep-app:latest` reconstruida 2026-07-17 14:06:xx CEST; `docker compose up -d --force-recreate
autopilot` → contenedor recreado 12:06:52Z. Confirmado en logs posteriores: sin más
`ModuleNotFoundError` para ningún conector en la ventana de observación (ver §1.2).

Por qué se corrige aquí y no solo se documenta: es un bug de una línea, reversible
(`requirements.txt` es texto plano, el commit se puede revertir), de alcance CLARO (11 módulos
enumerados por grep, no una suposición), y bloquea directamente el propio objetivo de F0
("el motor no se cae" — un motor que crashea 1 de cada 5 fuentes en cada intento no cumple esa
barra). Doctrina anti-atajo: atacar la causa, no maquillar con un "ya lo veré".
