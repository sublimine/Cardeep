# P05 — Cosechadores y capa de conectores unificada (enjaular cada inventario)

> Convertir ~44 conectores copy-paste (con un crash vivo y agendado en coches.net) en una flota gobernada por un contrato unico WholesaleConnector + un nucleo de persistencia parametrizado, con contract-testing por conector que hace imposible el drift de firmas.

**Mision:** Para el objetivo soberano (servir el inventario del 100% de puntos de venta de Espana con huella digital, delta vivo y receta re-ejecutable), la cosecha es el organo que ENJAULA cada inventario descubierto. Su forma de grado superior es: cada fuente (marketplace, OEM, grupo, web propia) entra como un PLUGIN que implementa un contrato unico, comparte UN solo motor de fetch/parse/ingest/delta/VAM, y se valida contra un contrato verificable antes de poder agendarse. El resultado: anadir el conector N+1 cuesta solo su delta especifico (payload + field_map), el delta (§5) y la receta ejecutable (§4) se cablean en UN punto y no en 29, y ningun conector puede crashear en produccion por drift de firma porque el contrato lo prohibe en CI.

## 2. Arsenal SOTA (investigado este 2026-06-20)

- **Singer Spec + Meltano SDK (singer-sdk)** _(libreria/estandar · Apache-2.0 · meltano/sdk activo (push 2026-06-20); el ecosistema Singer/Meltano tiene cientos de taps en produccion y es estandar de facto ETL desde 2017; spec estable)_
    - Es el patron de referencia mundial para 'enjaular cada fuente bajo un contrato unico': el Singer spec separa taps (extractores) de targets (cargadores) con un contrato de mensajes (SCHEMA/RECORD/STATE) y la SDK da clases base Stream/Tap que reducen ~70% el codigo por conector y fuerzan un STATE de cursor/bookmark estandar -- exactamente el problema de P05 (un contrato, un nucleo, deltas por fuente). El STATE como cursor incremental es el patron canonico para el delta vivo de CARDEEP. Se adopta el PATRON (clase base + spec de mensajes + bookmark), no la dependencia, evitando acoplar a su runtime.
    - <https://github.com/meltano/sdk>
- **pluggy** _(libreria · MIT · 1.641 stars, push 2026-06-16, mantenido por pytest-dev; usado por todo el ecosistema pytest -> produccion masiva)_
    - El sistema de plugins minimalista y production-ready que sostiene pytest y tox. Da hookspec/hookimpl: un nucleo declara los puntos de extension (fetch_page, build_payload, parse_item, field_map) y cada conector los implementa como hooks tipados y descubribles. Es la via mas madura para convertir 44 ficheros copy-paste en plugins registrables sin un framework pesado, y su modelo de 'specification + implementation' es el enforcement de contrato en runtime que P05 necesita. 1.641 stars suena modesto pero corre dentro de millones de instalaciones de pytest -> madurez extrema probada.
    - <https://github.com/pytest-dev/pluggy>
- **Crawlee for Python (Apify)** _(framework/repo · Apache-2.0 · 9.206 stars, push 2026-06-19, mantenido por Apify (empresa); releases frecuentes 2026)_
    - Framework de scraping de 2a generacion (post-Scrapy) con arquitectura de componentes desacoplada moderna y async-nativa: RequestQueue durable, Dataset, AutoscaledPool, gestion de sesiones/proxies y BasicCrawler como clase base extensible. Es la referencia 2025-2026 de 'connector base class + pipeline de items + storage' que valida el diseno objetivo de P05 (clase base + storage abstracto + sesiones gobernadas). Apache-2.0 (frente al BSD de Scrapy pero ecosistema Twisted legacy) y disenado para extraer datos para LLM/RAG. Se mina para patrones de base class y storage, no se adopta el runtime (CARDEEP ya tiene su governor/cage propio competitivo).
    - <https://github.com/apify/crawlee-python>
- **asyncpg COPY-to-staging + INSERT...ON CONFLICT FROM unnest (patron de bulk upsert)** _(tecnica · PostgreSQL/asyncpg Apache-2.0 · asyncpg (MagicStack) estandar de la industria, activo 2026; tecnica documentada y benchmarkeada en multiples fuentes 2025 (Tiger/Timescale, overflow.no))_
    - Es la tecnica SOTA 2025 para el corazon del _ingest_window unificado: COPY a una tabla staging UNLOGGED via asyncpg.copy_to_table() y luego un unico INSERT...ON CONFLICT...FROM staging dentro de la transaccion. Benchmarks: unnest()-SELECT ~3x mas rapido que VALUES multi-fila (~850k filas/s), y COPY supera a batch-INSERT por amplio margen en ingest puro. CARDEEP ya usa unnest (coches_net_wholesale.py:797-800) -> el salto SOTA es promover los volumenes altos a COPY+staging manteniendo el ON CONFLICT idempotente (misma semantica delta/VAM byte-for-byte). asyncpg sigue siendo el driver async PG mas rapido.
    - <https://overflow.no/blog/2025/1/5/using-staging-tables-for-faster-bulk-upserts-with-python-and-postgresql/>
- **Pact (pact-python, core en Rust) para contract testing de conectores** _(tecnica/libreria · MIT (pact-python) / contrato Pact estandar · Pact es el framework de contract testing mas adoptado (multi-lenguaje JS/Java/Python/Go/.NET), core Rust mantenido 2025-2026; integraciones CI (GitHub Actions, can-i-deploy))_
    - Contract testing consumer-driven: cada conector (consumer) declara el contrato que espera del nucleo de persistencia (provider) -- exactamente la pieza que falta y que habria detectado el bug de coches_net_facet:295 en CI antes de agendarlo. El core Pact esta en Rust expuesto por FFI (paridad multi-lenguaje, rapido). Para P05 el patron concreto es 'connector-vs-core contract': un test parametrizado que verifica que cada conector cumple el Protocol WholesaleConnector y que su llamada a ingest respeta la firma -- 'grep==1 definicion + todos cumplen el Protocol + paridad de inserts' (criterio del MASTER_PLAN §6:447) se vuelve un gate de CI ejecutable, no una aspiracion.
    - <https://docs.pact.io/implementation_guides/python/docs/consumer>

## 3. Arquitectura objetivo (10/10 institucional)

Diseno 10/10: una FLOTA DE CONECTORES-PLUGIN sobre UN nucleo unico. COMPONENTES: (1) `pipeline/platform/_core/contract.py` -- `WholesaleConnector` como typing.Protocol (runtime_checkable) que declara el contrato minimo: `spec() -> PlatformSpec`, `build_payload(cursor) -> Request`, `parse_items(raw) -> list[RawListing]`, `field_map() -> FieldMap`. Mas un dataclass `PlatformSpec` (trade_name, website, source_key, endpoint, host, data_surface, is_tier1, category_id) que absorbe las constantes-de-modulo hoy hardcoded en cada `ensure_platform_entity`. (2) `pipeline/platform/_core/persistence.py` -- UNA sola `ensure_platform_entity(conn, spec: PlatformSpec)` (mata las 29 copias) y UN solo `ingest_window(conn, geo, ctx: IngestContext, pages, state: HarvestState)` parametrizado por `field_map` (absorbe las 18 variantes; el tipo de pagina se normaliza a un `RawPage` unico antes de entrar). State-based cursor estilo Singer (bookmark por particion: province/price-band/segment) para que el delta sea incremental y reanudable. (3) `pipeline/platform/_core/ingest_engine.py` -- el motor bulk: para volumenes altos, COPY-to-staging UNLOGGED + INSERT...ON CONFLICT...FROM unnest dentro de UNA transaccion, preservando byte-for-byte la semantica delta/VAM/platform_listing/NEW-event ya correcta. (4) Registro de plugins via pluggy: cada conector se auto-registra; el scheduler descubre conectores por el registro, no por un dict hardcodeado de 50 SourceEntry. (5) `pipeline/platform/connectors/<source>.py` -- cada conector queda reducido a su DELTA: PlatformSpec + build_payload (la particion/facet especifica) + field_map + parse especifico. Los facets dejan de IMPORTAR del wholesale: comparten el nucleo, no se acoplan entre hermanos. CONTRATOS: el Protocol es el contrato estructural; un suite de contract-testing (estilo Pact provider verification) parametriza sobre TODOS los conectores registrados y verifica: (a) cada uno es instancia del Protocol, (b) su PlatformSpec valida contra schema, (c) un ingest dry-run contra una fixture produce los mismos counts que el camino legacy (paridad pre/post). DATOS: misma DB; staging tables transitorias; tablas core intactas. DECISIONES: adoptar PATRONES (Singer state/bookmark, pluggy hooks, Crawlee base-class, Pact provider-verification) NO los runtimes -- CARDEEP ya tiene governor/cage/VAM competitivos; importar frameworks pesados seria regresion. Migracion estrangulador (strangler): nucleo nuevo coexiste, conectores migran de a uno con paridad verificada, el legacy muere conector a conector.

## 6. Beyond-SOTA (la ambicion: mas alla del estado del arte)

Mas alla del estado del arte: contract-testing GENERATIVO + auto-deteccion de drift de payload del marketplace. (1) Ningun framework de scraping (Scrapy, Crawlee) ni de ETL (Singer/Meltano) ofrece hoy un gate que pruebe que CADA conector de una flota cumple un contrato estructural Y de paridad de datos como condicion de agendado -- CARDEEP lo convierte en invariante de CI (un coches_net_facet:295 se vuelve imposible de mergear). (2) El salto beyond-SOTA real: un 'contract sentinel' que, usando la captura de bytes crudos del evidence-store (Lente B/VAM §7), detecta cuando el SHAPE del JSON de un marketplace cambia (campos renombrados, anidamiento nuevo) ANTES de que el field_map produzca un parse silenciosamente vacio -- el modo de fallo mas insidioso y caro del scraping a escala, que ningun framework actual vigila. El conector se auto-cuarentena y emite un gestion_item con el diff exacto del shape, en vez de cosechar basura o ceros. Esto fusiona contract-testing (estatico) con schema-drift-detection (vivo sobre bytes reales), una combinacion que no existe empaquetada en 2026.

Si el plan guia decisiones de otros puntos, el error se propaga; reportar y corregir el plan, y disenar el refactor sobre la realidad (PlatformSpec), no sobre el 'reemplazo mecanico' que el plan asume.
